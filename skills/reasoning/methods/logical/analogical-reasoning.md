# Analogical Reasoning

## Purpose
Analogical reasoning transfers knowledge from a well-understood source domain to a less familiar target domain by identifying structural correspondences between them. It answers "what is this like?" and uses the answer to generate insights, predictions, or solutions.

## When to Use
- When facing a novel problem that resembles a known problem in structure but not in surface features.
- When you need to explain a complex concept by mapping it to a familiar one.
- When exploring cross-domain innovation — solutions from one field applied to another.
- When direct reasoning in the target domain is blocked by missing knowledge.

## When Not to Use
- When the source and target domains are only superficially similar — analogical reasoning on surface features produces false analogies.
- When precision is required and the analogy cannot be validated.
- When the target domain is well-understood and direct reasoning is available.
- When the analogy would import misleading assumptions from the source domain.

## Problem Signals
- The problem contains "this is like," "similar to," "analogous to," "reminds me of," "what if we treated X as Y."
- The user is stuck and says "I don't know how to think about this" — they need a familiar frame.
- The problem is in a novel domain but the user has expertise in a different domain.
- The user describes a problem structure that matches a known pattern from another context.

## Inputs
- A source domain (well-understood, with known structure and behavior).
- A target domain (less familiar, but believed to share structural properties).
- A mapping hypothesis: what corresponds to what between source and target.

## Procedure
1. **Characterize the source domain.** What are the key entities, relationships, and causal mechanisms in the source? Be precise about the structure, not just the surface features.
2. **Characterize the target domain.** What is known about the target? What entities and relationships exist? What is unknown?
3. **Identify structural correspondences.** Map entities from source to target based on their roles in the structure, not their surface similarity. A pump in a hydraulic system might map to a battery in an electrical circuit — both are "pressure sources."
4. **Check for systematicity.** A good analogy maps higher-order relations (causal structures, functional roles), not just isolated attributes. The mapping should preserve the relational system.
5. **Identify where the analogy breaks.** Every analogy has limits. What aspects of the source domain have no correspondence in the target? What would be misleading to import?
6. **Transfer insights.** Given the mapping, what can be inferred about the target? What does the source domain predict about the target's behavior?
7. **Validate.** Can the transferred insight be tested independently? Is there evidence in the target domain that supports or contradicts the analogy?

## Output
- An explicit mapping between source and target entities and relationships.
- Insights transferred from source to target.
- The boundaries of the analogy: what it does and does not imply.
- Testable predictions generated by the analogy.

## Strengths
- Handles novelty — when you have no direct experience, analogical reasoning provides a starting point.
- Cross-domain insight — solutions from one field can be creatively applied to another.
- Pedagogical power — complex ideas become accessible when mapped to familiar concepts.
- Generates testable hypotheses in unfamiliar domains.

## Limitations
- False analogies: surface similarity without structural correspondence leads to wrong conclusions.
- Analogy boundaries are often missed: users import assumptions from the source that do not hold in the target.
- No guarantee of correctness: even a structurally sound analogy may fail if the target has unique properties.
- Difficult to formalize: structural mapping requires understanding of both domains.

## Common Failure Modes
- **Surface analogy.** Mapping based on superficial features ("a cell is like a factory because both have walls") without structural correspondence. Always check: do the relational structures actually align?
- **Overextending the analogy.** Importing every property of the source into the target. Every analogy breaks somewhere — identify the breaking points explicitly.
- **Single-analogy fixation.** Using only one analogy and treating it as truth. Generate multiple analogies for the same target and compare their implications.
- **Ignoring disanalogies.** Focusing only on correspondences and ignoring where the domains differ. The disanalogies are often more informative than the analogies.
- **Analogy as argument.** Using an analogy to persuade rather than to explore. "X is just like Y, therefore we should do Z" is rhetoric, not reasoning.

## Verification
- Does the mapping preserve relational structure, not just attribute similarity?
- Are there alternative analogies that map the target domain differently?
- Can the predictions from the analogy be tested independently of the analogy itself?
- Where does the analogy break? Have these boundaries been explicitly stated?

## Combine With
- **First-principles reasoning** — use analogy to generate initial hypotheses, then first-principles to validate them from fundamentals.
- **Systems thinking** — use analogy to identify system structures (feedback loops, stocks, flows) in the target domain.
- **Deductive reasoning** — once the analogy establishes a structural correspondence, use deduction to derive consequences.
- **Divergent thinking** — use multiple analogies in parallel to explore the target from different perspectives.

## Example
**Problem:** A team is designing a rate-limiting system for an API. They are unsure how to handle burst traffic gracefully.

**Application:**
1. Source domain: A highway on-ramp with a traffic light that meters cars entering the freeway.
2. Target domain: An API rate limiter managing request bursts.
3. Structural mapping:
   - Cars → API requests
   - Highway capacity → Server capacity
   - On-ramp meter → Rate limiter
   - Traffic jam → Server overload
   - Meter rate → Tokens per second
   - On-ramp queue → Request queue
4. Systematicity check: The causal structure matches — both systems have a constrained resource, an inflow, a metering mechanism, and a queue that forms when inflow exceeds capacity.
5. Transferred insights:
   - A fixed-rate meter (token bucket) allows short bursts but prevents sustained overload.
   - Queue length matters: if the queue grows unbounded, requests eventually time out (cars run out of gas).
   - Dynamic metering (adjusting rate based on downstream capacity) is more efficient than fixed-rate metering.
6. Analogy boundaries: Unlike cars, API requests can be dropped without consequence if the client retries. Drivers don't "retry" a missed green light.
7. Validation: The insights match known rate-limiting algorithms (token bucket, leaky bucket, adaptive rate limiting).
